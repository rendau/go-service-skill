# Сервисные модули — `internal/service/<module>`

Конвенция организации модулей сервисного слоя в проектах на базе **gotemplate**. Модули
`internal/service/*` — это фоновые процессы, интеграции с внешними системами и выделенные/
переиспользуемые логики. Они могут использовать другие сервисы `internal/service/*` и доменные
сервисы `internal/domain/*/service`, но **не обращаются в usecase-слой**.

Связанные скиллы: `crud` (доменный CRUD-стек), `mobone` (repo-слой), `golang-samber-lo` (`lo`).

---

## Область применения

- **Полный набор** (`model/` + `service/model/`) — модулям-**клиентам внешних систем**
  (HTTP/gRPC/SDK/брокер): у них есть свой внешний формат данных, который надо изолировать от домена.
- **Внутренние** модули (инфраструктура, оркестрация, вычисления — без своего внешнего формата)
  получают только структурную часть (`service/` + фасад); `model/`/`service/model/` им не
  обязательны (они оперируют доменными моделями или примитивами).

---

## Раскладка модуля

```
<module>/
├── interface.go            # пакет <module> — ФАСАД: что модуль предоставляет
├── model/                  # пакет model — контрактные модели (вход/выход публичных методов)
└── service/
    ├── service.go          # пакет service — реализация + конструктор New (логика в неск. файлах)
    ├── interface.go        # пакет service — порты ЗАВИСИМОСТЕЙ модуля (если они есть)
    ├── constant/
    │   └── constant.go     # пакет constant — локальные константы модуля (если они есть)
    └── model/              # пакет model — локальные/транспортные модели для своих нужд
```

- В **корне** модуля — только фасадный `interface.go` и (при необходимости) контрактные модели в
  `model/`. Реализации, локальных моделей и локальных констант в корне нет; вся логика — в
  подпакете `service`.
- `model/`, `service/model/`, `service/interface.go`, `service/constant/` создаются
  **только когда нужны**.

---

## Фасад (корневой `interface.go`)

- Есть **всегда**, даже если ни один потребитель его напрямую не использует — «витрина»
  возможностей модуля, перечисляет все публичные методы.
- Имя интерфейса **не обязано** повторять имя модуля — допустимо короткое/ролевое (модуль
  геокодирования может экспонировать `Geocoder`).
- Конструктора в фасаде нет.

```go
// internal/service/geocoder/interface.go
package geocoder

import (
	"context"

	geocoderModel "<module-path>/internal/service/geocoder/model"
)

type Geocoder interface {
	Geocode(ctx context.Context, address string) (geocoderModel.Point, error)
}
```

---

## Конструктор

- Живёт в `service` и **возвращает конкретный тип** (`*Service`), не интерфейс
  («accept interfaces, return structs»).

```go
// internal/service/geocoder/service/service.go
package service

func New(deps ...) *Service { ... }
```

---

## Зависимости (`service/interface.go`)

- Если модуль зависит от других сервисов, узкие порты этих зависимостей объявляет **сам модуль** в
  **`service/interface.go`**.
- Не путать с фасадом: фасад = что модуль *предоставляет*; `service/interface.go` = что модуль
  *требует* извне.

```go
// internal/service/geocoder/service/interface.go
package service

type cacheI interface {
	Get(ctx context.Context, key string) ([]byte, bool)
	Set(ctx context.Context, key string, val []byte)
}
```

---

## На стороне потребителя

В местах использования потребитель объявляет **свои** (по возможности узкие) интерфейсы того, что
реально вызывает, и **не зависит** от пакета модуля. Фасад и порт потребителя сосуществуют: фасад —
каталог возможностей, порт потребителя — конкретный минимальный срез.

---

## Модели

- `<module>/model/` — **контракты** (вход/выход публичных методов). **Чистые**, без тегов
  сериализации/хранилища.
- `<module>/service/model/` — **локальные/транспортные** структуры (зеркало внешнего формата), с
  тегами + конвертеры `Encode*`/`Decode*`. Транспортные типы клиентов внешних систем подписывай
  суффиксами **`*Req`/`*Rep`** там, где это логично.
- Оба пакета называются `model` — в импортах различай алиасами (контракт — `<module>Model`,
  локальный — `localModel`). Зависимость только `service/model` → `model`.
- Если тип одновременно контракт и транспорт — **разделять**: чистый контракт в `model`,
  транспортное тело + `Encode` в `service/model`.
- Файлы — по сущностям (`<entity>.go`); общее для пакета — `base.go`; внутри файла — секции с
  короткими комментариями-метками.

---

## Константы

- **Общие/контрактные** (значения, которыми обмениваются несколько слоёв/модулей: источники,
  провайдеры, статусы) — в общем пакете констант (`internal/constant`) с понятным префиксом;
  правило «не зависеть от модуля» на них **не распространяется**.
- **Локальные** константы модуля (нужны только его реализации) — в **`service/constant/constant.go`**
  (пакет `constant`, в импортах — под алиасом `localConstant`, чтобы не путать с глобальным
  `constant`). Сюда же — локальные `var`-данные и большие текстовые ресурсы (напр. промпты в
  `prompts.go`).

---

## HTTP-транспорт клиентов внешних систем

Модули-клиенты внешних HTTP-API **не используют общий http-хелпер/обёртку** — каждый строит запросы
на стандартном `net/http` через свой приватный метод `sendRequest`. Полная конвенция, сигнатуры,
мульти-провайдер и настройка `http.Client` — в `references/http-client.md`.

## Чеклист модуля

- [ ] Корень: фасадный `interface.go` (пакет `<module>`) — есть всегда
- [ ] `model/` — контрактные модели без тегов (только для клиентов внешних систем)
- [ ] `service/service.go` — `*Service` + конструктор `New` (return struct)
- [ ] `service/interface.go` — узкие порты зависимостей (если есть)
- [ ] `service/model/` — транспортные `*Req`/`*Rep` с тегами + `Encode*`/`Decode*` (если есть)
- [ ] `service/constant/constant.go` — локальные константы под `localConstant` (если есть)
- [ ] HTTP-клиент: приватный `sendRequest`, явно настроенный `http.Client` (см. references)
- [ ] Потребитель объявляет свой узкий интерфейс, не зависит от пакета модуля
- [ ] Регистрация в `internal/app/app.go` (алиас-конструктор с суффиксом `P`)
